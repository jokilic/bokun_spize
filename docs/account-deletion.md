# Account deletion

The app reauthenticates the current Firebase user, refreshes their ID token, and finishes provider revocation before submitting the request. For Apple, it exchanges the fresh Apple authorization code through Firebase Auth's revocation API. For Google, it disconnects Google Sign-In. Email/password accounts have no provider grant to revoke. If revocation fails, the user can retry from reauthentication while the Firebase account still exists. Provider credentials and authorization codes stay out of the deletion job. [Firebase Apple sign-in guidance](https://firebase.google.com/docs/auth/ios/apple)

`requestAccountDeletion` accepts requests with App Check and Firebase authentication. Creating a job requires an unrevoked Firebase session authenticated within the past five minutes. The callable uses the authenticated UID and treats repeat requests for an existing job as accepted. The UID-only job is durable before the app signs out. Legacy app versions and single-account Auth deletions outside the app enqueue cleanup through `cleanupDeletedUser`. Use single-user Auth deletion for operational requests so the Auth trigger runs. [Firebase Auth session behavior](https://firebase.google.com/docs/auth/admin/manage-sessions) · [Firebase Auth deletion events](https://firebase.google.com/docs/functions/auth-events)

The scheduled worker checks for work every five minutes. It deletes the Auth user first to stop new sessions, then allows a short drain period for work already in flight. The job blocks Firestore and Storage access with cached credentials, and server-side meal and notification writers check it as well. The worker recursively deletes `users/{uid}`, including nested documents whose parents are missing, AI claims and quota records, notification data, meals, and weight tracks. It deletes root `contactMessages` by `userUid`, so messages sent before an email change are covered. Support messages remain while the account is active unless an admin deletes them sooner.

Storage cleanup deletes all object generations under `users/{uid}/` in the app bucket. The account stays blocked until a final Storage sweep eight days after the initial cleanup, covering uploads that finish from previously issued resumable sessions. After the final sweep, the worker removes the job record. Cloud Storage soft-delete and backup retention follow the project's configured policies. [Cloud Storage resumable uploads](https://docs.cloud.google.com/storage/docs/resumable-uploads) · [Cloud Storage soft delete](https://docs.cloud.google.com/storage/docs/soft-delete)

## Rollout and recovery

Deploy the updated Functions, Firestore rules, and Storage rules before releasing the app client. Enable the Firebase Rules Firestore Service Agent permission when CLI or console prompts for cross-service Storage rules. Verify the scheduler's runtime service account can delete Auth users, read and write Firestore, and list and delete objects in `bokun-spize-eu`. [Cross-service rules permissions](https://firebase.google.com/docs/rules/manage-deploy#manage_permissions_for_cross-service_cloud_storage_security_rules)

An interrupted or failed phase becomes eligible again when its ten-minute lease expires. Monitor scheduler failures and the `Account deletion will retry` log for repeated permission or retention errors. Once the underlying issue is fixed, the scheduler resumes the same job. Keep pending job records in place to preserve the write block and retry state.

For accounts confirmed deleted before this flow was deployed, operators can enqueue cleanup for the original UID using `enqueueAccountDeletion(firestore, uid, true)` from a trusted Admin environment. This also removes any remaining contact messages for that UID. Keep Firebase Auth UIDs unique across account lifetimes.
